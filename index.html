06 / 规则：能约束什么？
真实菜单：Settings → Tags, Rules、PII Settings、Semantic Input、Agent Settings。区分标签规则、业务规则、访问权限。
原生功能
Tags / Rules
对目录与本体重放标签规则；用于分类和治理标记，不能直接视为 SQL 强制访问控制。
原生功能
Semantic Input
补充术语表定义与自定义 Prompt，影响回答，但 Prompt 不等于硬权限。
原生功能
Agent Settings
配置 SQL timeout、SQL 结果可视化。
推荐扩展
Query Policy Gateway
执行 SQL AST 校验、禁止 DDL/DML、数据源只读、行数/字节/时间限制、租户权限。
模拟规则判定
仅演示思路，不能用于生产安全审查；生产应使用 SQL parser / AST 和数据库权限。

09 / 本体无法回答、SQL 失败怎么办？
推荐用受控决策树，而不是直接让模型猜字段或无条件访问原始数据库。
check_answerable
→
覆盖充分？
→
ask_question
→
验证 SQL / Rows / 口径
情况 A · 缺业务术语
检索相关 Term → 补充 glossary / SQL attribute → 人工审核 → 回归问数。
情况 B · 缺字段映射或关系
检查 column attributes / semantic foreign keys，确认 Join 基数与时间维度后修正。
情况 C · SQL 语法或执行失败
系统已有检查与修复流程；仍失败时保留错误证据，修正模型或数据源配置。
情况 D · 权限不足或数据源不可达
停止，不自动绕过权限或切到其他未授权数据源；提示用户处理。
情况 E · 结果太大
改写为数据库侧聚合，或交给受控 Go Query Executor；不要把百万行传入 MCP/LLM。
情况 F · 业务定义冲突
停止正式回答，生成语义反馈工单，业务审核通过后发布与回归。
模拟一次“失败 → 反馈 → 修正”


10 / 五问总结与实施验收
问题 1
如何自动建模？
Connections → Ingestion → Semantic Compilation → 检查 Terms、SQL Attributes、Relationships → Chat 验证与人工认证。
问题 2
如何外部补充？
原生 / Ossie YAML 走 Import；SQL、Excel、PRD、代码先抽取并转成受支持的模型格式，再审核导入。
问题 3
如何作为 MCP？
部署 MCP :3003，OAuth 登录，Business Agent 同时使用业务 Skill 与通用 Query Skill，调用只读 MCP 工具。
问题 4
SQL 无法回答怎么办？
先判断覆盖缺失、映射错误、SQL 错误、数据不可用或权限问题；能修模型则修，不能则明确拒绝猜测。
问题 5
如何规则约束？
Tags/Rules 用于治理标记，Semantic Input 用于软约束；强制 SQL/权限控制应依靠服务端策略和数据库权限。
